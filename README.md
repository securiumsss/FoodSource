# FoodSource

Прототип B2B-сервиса для поиска и сравнения поставщиков продуктов, ингредиентов и упаковки. Сценарий закупщика: **поиск и фильтры → оценка условий → сравнение до четырёх компаний → заметки и статус → запрос коммерческого предложения**.

Каталог построен на данных из открытых страниц компаний. Оценка помогает расставить приоритеты, но не подтверждает действительность документов, цен и условий доставки. Перед закупкой их необходимо проверить у поставщика.

## Архитектура

- **TypeScript-монорепозиторий** на npm workspaces: `shared/` содержит общие типы API и модели для клиента и сервера.
- **React + Vite + Tailwind CSS** — адаптивный каталог, фильтры, сравнение, карточка с источниками и шаблоном КП.
- **NestJS** — API и детерминированный скоринг. Локально и в Docker по умолчанию работает SQLite с авто-сидингом; в облаке NestJS подключается к Supabase PostgreSQL через серверный `DATABASE_URL`.
- При `npm start` и в Docker NestJS раздаёт API и SPA с одного порта. На Vercel SPA раздаётся как статические файлы, а `/api/*` обслуживает одна Node.js Function.

```text
shared/src/       Общие типы и контракты
backend/src/      NestJS: поставщики, скоринг, SQLite / PostgreSQL и health
frontend/src/     React: API-клиент, компоненты и каталог
data/             Сид, схема PostgreSQL и локальная SQLite-база
scripts/          Проверка сида, миграция и упаковка для Vercel
```

## Скоринг: до 100 баллов

| Критерий | Вес | Расчёт |
| --- | ---: | --- |
| Регион и покрытие | 30 | При выбранном регионе: подтверждённое местное покрытие — 30, «Вся РФ» — 22, иначе 0. Без выбора: 26 за «Вся РФ», 22 за несколько регионов, 18 за один; ещё 4 за указанный срок, максимум 30. |
| Документы и комплаенс | 25 | Документы и системы — 25; что-то одно — 18; ничего не указано — 0. |
| Прозрачность и контакты | 25 | Числовой MOQ — 10; ценовой ориентир — 8; телефон и email — 7, один из них — 4, иначе — 1. |
| Логистика и запрос | 20 | Своя доставка — 7; соответствие лимиту MOQ — 5, неизвестный или нерублёвый MOQ — 2. Молочная продукция и заморозка: температурный режим — 8; без лимита MOQ вместо баллов за лимит начисляется 5 за указанный срок доставки, иначе 2. Упаковка и специи: срок и опубликованные условия доставки — 5 и 3, либо 8 и 5 без лимита MOQ. |

Вердикты: от 75 — «Рекомендуем связаться в первую очередь», 55–74 — «Хороший вариант», ниже 55 — «Требует уточнений». Каждая оценка сопровождается разбивкой и вопросами для уточнения. Отсутствие данных не означает отсутствие услуги или документа; `pricingNote` сохраняет ограничения цен и условий. Цены разных товаров не следует напрямую сравнивать как единый прайс-лист.

При выборе города учитывается покрытие «Москва и МО» или «Санкт-Петербург и ЛО», но не наоборот: доставка в город не обещает доставку по области. При выборе региона показываются также компании с покрытием «Вся РФ». Фильтр максимального MOQ по умолчанию включает неизвестные и нерублёвые значения; это можно отключить. При равной максимальной оценке в сравнении лидером считается первый выбранный поставщик, при этом все равные лидеры отмечены в таблице.

## Данные

`data/suppliers.seed.json` содержит 21 реального поставщика по четырём категориям. В записях сохранены страницы-источники, известные условия и явно неизвестные значения. `scripts/validate-seed.mjs` проверяет типы, контакты, дубли и покрытие; полная проверка дополнительно обращается к сайтам. Антибот-защита и временная недоступность сайтов могут влиять на её результат.

Пилот «Ассортимент» содержит восемь позиций из открытых каталогов трёх поставщиков молочной продукции. Для каждой сохранены страница товара и дата проверки. Опубликованная цена относится к конкретному товару, не является актуальной офертой и не подтверждает наличие. Пилот дополняет каталог на уровне API и не требует миграции SQLite или Supabase. Пример сценария: поиск «сливки 33%» → сравнение совпавших позиций → добавление товара и фасовки в запрос КП. Позиции собраны вручную; автоматического обновления пока нет.

Сидинг **идемпотентен**: он добавляет отсутствующие записи и не перезаписывает поставщиков, статусы или заметки в существующей базе. Изменение JSON не обновляет уже загруженные записи; для этого необходима отдельная миграция. База по умолчанию — `data/app.db`.

## Запуск

Требуется Node.js **22.12+** и npm. Для сборки `better-sqlite3` при отсутствии готового бинарного файла могут понадобиться Python, `make` и C++-компилятор.

```sh
npm ci
npm run dev                    # Vite и NestJS; API проксируется на :3000
```

Откройте адрес Vite из консоли (обычно `http://localhost:5173`). Production-сборка и проверки:

```sh
npm run build && npm start    # SPA и API на http://localhost:3000
npm test                      # Jest и Vitest: backend и основные сценарии интерфейса
npm run validate:seed:local   # без сетевых запросов
npm run validate:seed         # включая HTTP-проверку источников
```

Настройки можно передать в окружении или скопировать `.env.example` в `.env`. `PORT` по умолчанию равен `3000`. Относительный `DATABASE_PATH` разрешается от каталога `backend/`, а абсолютный используется напрямую.

### Docker

```sh
docker build -t foodsource .
docker run --rm -p 3000:3000 -v foodsource-data:/app/storage foodsource
```

Образ содержит собранный SPA и исходный сид; база автоматически создаётся в `/app/storage/app.db`. Именованный том сохраняет статусы и заметки между перезапусками и не скрывает сид. Порт можно изменить через `PORT` и соответствующий проброс `-p`.

### Vercel + Supabase

1. Создайте проект Supabase. В **Connect** скопируйте URI **Session pooler** и задайте его в локальном `.env` как `DATABASE_MIGRATION_URL`. Подставьте пароль базы (спецсимволы в пароле закодируйте для URL). Не коммитьте этот файл. TLS с проверкой сертификата включён по умолчанию; при необходимости задайте корневой сертификат Supabase через `DATABASE_CA_CERT`.
2. Подготовьте схему и каталог: `npm ci`, затем `npm run db:migrate`. Чтобы также перенести статусы и заметки из локальной базы, выполните вместо этого `npm run db:migrate -- --from-sqlite data/app.db`. Команда читает SQLite без записи, добавляет 21 поставщика и не перезаписывает изменённые записи в PostgreSQL. Не переносите личные заметки в БД публичной демоверсии.
3. Импортируйте репозиторий в Vercel **из корня монорепозитория**, Framework Preset — **Other**, Node.js — **22.x**. Оставьте Output Directory без переопределения: `vercel.json` запускает `npm run build:vercel`, который формирует `.vercel/output` со статикой и функцией. Если Git-репозиторий не настроен, после `npx vercel link` и настройки переменных можно собрать артефакт локально и использовать `npx vercel deploy --prebuilt`.
4. В Vercel задайте `DATABASE_URL` из **Transaction pooler** (порт `6543`). Это серверная переменная: не добавляйте префикс `VITE_` и не передавайте строку подключения клиенту. Настройте нужные окружения и не подключайте общедоступные preview-деплои к базе с рабочими заметками. После деплоя проверьте `/`, `/api/health` и сохранение статуса после перезагрузки.

Схема PostgreSQL не доступна через Supabase Data API по умолчанию; браузер работает только с NestJS. **В приложении пока нет входа и изоляции пользователей:** закройте весь деплой, включая API, через Deployment Protection или используйте приватный доступ. У всех допущенных пользователей статусы и заметки общие.

## API

- `GET /api/health` — состояние сервера и количество поставщиков.
- `GET /api/suppliers` — поиск, фильтры, сортировка и фасеты; параметры описаны в `SuppliersQueryParams`.
- `GET /api/suppliers/:id` — карточка и шаблон КП; `region` и `maxMoqRub` задают контекст оценки.
- `POST /api/suppliers/compare` — сравнение 2–4 уникальных ID с необязательными `region` и `maxMoqRub`.
- `PATCH /api/suppliers/:id/workspace` — сохранение статуса и заметок до 2000 символов.

## Как развивать сервис в продакшене

- Добавить гибридный живой поиск: Search API для обнаружения страниц и LLM-экстракцию фактов с обязательными ссылками на первоисточники и проверкой человеком.
- Дедуплицировать компании по ИНН и домену, хранить происхождение и дату каждого утверждения.
- Контролировать актуальность прайсов и документов: сроки действия, периодические проверки, уведомления об устаревших данных.
- Добавить версионирование миграций PostgreSQL, резервное копирование и отдельную роль БД для API.
- Ввести роли и аккаунты закупщиков, изоляцию рабочих пространств и историю коммуникаций. Текущий прототип не содержит аутентификации и не предназначен для публичного размещения персональных данных.
